# Requirements Document

## Introduction

This document covers three major enhancements to the CricketVerse.AI platform:

1. **Deep Ball-by-Ball AI Analysis** — richer, context-aware AI insights delivered on every ball rather than every third ball, with categorised insight types, confidence scores, and historical pattern references.
2. **Real-Time Multi-Match Scoreboard** — a dedicated, always-visible scoreboard widget on the Home page that polls all live matches simultaneously and lets users click through to any individual match.
3. **Upcoming Cricket Tournaments Block** — a section on the Home page showing upcoming series and tournaments sourced from the Cricbuzz RapidAPI `/series/v1/upcoming` endpoint, styled consistently with the existing dark cricket-themed design system.

All three enhancements must integrate with the existing FastAPI backend (`backend/main.py`), the Redux store (`matchSlice.ts`), the Panel component system, and the Tailwind v4 / dark-theme CSS defined in `index.css`.

---

## Glossary

- **AI_Analyzer**: The backend subsystem responsible for generating ball-by-ball AI insights, including pattern detection, pressure scoring, and win-probability shift calculation.
- **Scoreboard_Widget**: The frontend React component that displays live scores for all concurrent matches on the Home page.
- **Scoreboard_Slice**: The Redux slice that manages the state of all live matches fetched for the scoreboard.
- **Tournament_Block**: The frontend React component that displays upcoming cricket series and tournaments on the Home page.
- **Tournament_Provider**: The backend class that fetches and normalises upcoming series data from the RapidAPI `/series/v1/upcoming` endpoint.
- **LiveMatchEngine**: The existing backend simulator class used when RapidAPI is not configured.
- **RapidApiCricketProvider**: The existing backend adapter class for the Cricbuzz RapidAPI.
- **Panel**: The existing reusable React UI component (`Panel.tsx`) used for all card-style sections.
- **BallChip**: The existing React atom component that renders a single ball result chip.
- **Insight**: A structured AI-generated analysis object containing a title, descriptive text, type, color, and confidence score.
- **Match_Card**: A single match entry within the Scoreboard_Widget showing team names, scores, and match status.
- **Tournament_Card**: A single tournament entry within the Tournament_Block showing name, dates, format, teams, and status.
- **Simulator_Fallback**: The mode in which the backend uses LiveMatchEngine data when RapidAPI is unavailable (i.e., `RAPIDAPI_KEY` is empty or `RapidApiCricketProvider.enabled` returns `False`).
- **EARS**: Easy Approach to Requirements Syntax — the pattern language used for all acceptance criteria below.
- **consecutive dot balls**: A sequence of ball results all equal to `"0"` with no intervening non-zero result within the same innings.
- **win-probability shift**: The absolute difference in percentage points between `winProbability.teamA` before and after a ball result is applied.
- **phase boundary**: The first ball of over 6 (end of Powerplay) or over 16 (start of Death overs) in a T20 match, or over 10 and over 40 in a 50-over match.

## Requirements

### Requirement 1: Deep Ball-by-Ball AI Analysis

**User Story:** As a cricket fan watching a live match, I want richer AI-powered insights delivered on every ball, so that I can understand the tactical context, pressure dynamics, and statistical patterns behind each delivery in real time.

#### Acceptance Criteria

1. WHEN a ball result is generated by the LiveMatchEngine or received from the RapidApiCricketProvider, THE AI_Analyzer SHALL produce an Insight object for every ball without exception.

2. THE AI_Analyzer SHALL generate Insights from at least six distinct categories: `momentum`, `pattern`, `pressure`, `matchup`, `prediction`, and `milestone`. Each Insight object SHALL include a `type` field set to one of these six values.

3. WHEN the ball result is a wicket (`"W"`), THE AI_Analyzer SHALL always produce an Insight of type `milestone` whose `text` field includes both the name of the dismissed batsman and the numeric win-probability shift (in percentage points) caused by the wicket.

4. WHEN a ball result is a six (`"6"`) or four (`"4"`) AND the win-probability shift for that ball is greater than zero, THE AI_Analyzer SHALL produce an Insight of type `momentum` whose `text` field states the win-probability shift in percentage points. IF the win-probability shift is zero, THE AI_Analyzer SHALL produce an Insight of type `pattern` instead.

5. WHEN a ball result is processed AND the rolling window of the last 12 ball results contains five or more consecutive `"0"` values ending at the current ball, THE AI_Analyzer SHALL produce an Insight of type `pressure`. In a second innings (chase), the `text` field SHALL state the dot-ball count and the current required run rate. In a first innings, the `text` field SHALL state the dot-ball count and the current run rate without referencing a required run rate.

6. THE AI_Analyzer SHALL include a `confidence` field (integer in the range 0–100 inclusive) in every Insight object. The `confidence` value SHALL be deterministically derived from the match state (e.g., based on over number, wickets fallen, and ball type) and SHALL NOT be a purely random number.

7. WHEN the first ball of a phase boundary over is processed (over 6 or over 16 in T20; over 10 or over 40 in a 50-over match) AND the previous ball was in the preceding phase, THE AI_Analyzer SHALL produce an Insight of type `milestone` whose `text` field names the new phase (e.g., "Middle overs", "Death overs").

8. THE AI_Analyzer SHALL populate the `bowler` and `batsman` fields in every Insight `text` string using the actual player names from the current match state at the time the ball is processed. Placeholder strings such as `{bowler}` or `{batsman}` SHALL NOT appear in any broadcast Insight.

9. WHEN the backend is operating in Simulator_Fallback mode (i.e., `RapidApiCricketProvider.enabled` is `False`), THE AI_Analyzer SHALL produce Insights on every ball using the state from `LiveMatchEngine`, applying the same category selection and confidence logic as in live mode.

10. THE AI_Analyzer SHALL track the `title` field of the last two Insight objects produced. IF the title of the current Insight matches either of the last two titles, THE AI_Analyzer SHALL select a different Insight template from the same category before broadcasting.

11. WHEN an Insight is broadcast over the WebSocket, THE System SHALL send it as a message with `type` equal to `"AI_INSIGHT"` and a `data` field containing the full Insight object including the `confidence` field.

12. THE LiveMatch page SHALL display the `confidence` field as a numeric badge (e.g., "87% confidence") rendered in a `text-xs` span adjacent to the Insight title within the AI Insight panel.

13. WHEN the LiveMatch page receives an `"AI_INSIGHT"` WebSocket message, THE LiveMatch page SHALL apply the `animate-slide-up` CSS class to the Insight panel container for the duration of the animation, replacing any previously displayed Insight.

14. THE AI_Analyzer SHALL maintain a rolling window of the last 12 ball result strings (e.g., `["0","1","4","W","0","0","6","0","0","0","0","1"]`) and use this window exclusively when computing `pressure` (consecutive dot count) and `pattern` (boundary clustering, wicket clustering) Insights.

### Requirement 2: Real-Time Multi-Match Scoreboard

**User Story:** As a cricket fan on the CricketVerse.AI Home page, I want to see live scores for all ongoing matches in a dedicated scoreboard section, so that I can monitor multiple games simultaneously and navigate to any match for deeper analysis.

#### Acceptance Criteria

1. THE System SHALL expose a `/api/matches/live` REST endpoint that returns a JSON object with a `matches` array, where each element is a match object normalised to the existing `ScoreData` schema plus a non-empty string `matchId` field.

2. WHEN the RapidApiCricketProvider is enabled, THE `/api/matches/live` endpoint SHALL fetch data from the RapidAPI `/matches/v1/live` path and include all matches returned by the API in the `matches` array, not only the first match.

3. WHEN the RapidApiCricketProvider is not enabled (Simulator_Fallback mode), THE `/api/matches/live` endpoint SHALL return a `matches` array containing exactly one entry: the current simulated match from the LiveMatchEngine, with `matchId` set to the stable string `"sim-match-1"`.

4. IF the RapidAPI request to `/matches/v1/live` fails for any reason, THEN THE `/api/matches/live` endpoint SHALL return a JSON response with HTTP status 502 containing a `fallback` field set to the simulated match object and an empty `matches` array.

5. THE Scoreboard_Widget SHALL be rendered on the Home page as the first visible section, above the Tournament_Block and above the existing PulsePlay Arena grid.

6. THE Scoreboard_Widget SHALL display each live match as a Match_Card. Each Match_Card SHALL show: team A short name, team A score (runs/wickets), team B short name, team B score (runs/wickets), current over (e.g., "14.4"), run rate (e.g., "9.60"), match format badge (e.g., "T20", "ODI"), and a live status indicator.

7. WHEN the Scoreboard_Widget contains more than four Match_Cards, THE Scoreboard_Widget SHALL render all cards in a single horizontally scrollable row with `overflow-x: auto` and `flex-nowrap`, so that no card wraps to a second line.

8. THE Scoreboard_Widget SHALL start a polling interval of exactly 15 seconds on component mount and clear the interval on component unmount. On each poll, it SHALL call `/api/matches/live` and update the Redux Scoreboard_Slice with the new match list without triggering a full page reload.

9. WHEN a Match_Card is clicked, THE System SHALL navigate the user to the path `/match/:matchId` using React Router, where `:matchId` is the `matchId` value from the clicked match's data object.

10. THE Scoreboard_Slice SHALL be a Redux Toolkit slice that stores: a `matches` array of `ScoreData & { matchId: string }` objects, a boolean `loading` flag, and a `lastUpdated` number (Unix timestamp in milliseconds). These three fields SHALL be the only top-level fields in the slice state.

11. WHEN the Scoreboard_Widget mounts and `loading` is `true` in the Scoreboard_Slice, THE Scoreboard_Widget SHALL render four skeleton placeholder cards. Each skeleton card SHALL have the same fixed width and height as a real Match_Card and SHALL use a pulsing grey background (`animate-pulse` with `bg-slate-700/30`).

12. WHEN the Scoreboard_Widget receives updated match data and a match's `teamAScore` or `teamBScore` value has changed from the previous render, THE Scoreboard_Widget SHALL apply the `animate-score-pop` CSS class to the changed score element for exactly one animation cycle (400 ms), then remove the class.

13. THE Match_Card SHALL be styled using the existing design tokens: `panel` class for the card container, `badge-live-red` for the live status indicator, and `badge-live-cyan` for the format badge. The card border SHALL use `border-[rgba(56,189,248,0.12)]` consistent with other panels on the page.

14. WHEN a match object in the `matches` array has `inningsStatus` equal to `"complete"`, THE Match_Card for that match SHALL render a "Final" label using the `badge-live-cyan` CSS class in place of the live status indicator.

15. WHEN the `matches` array in the Scoreboard_Slice is empty and `loading` is `false`, THE Scoreboard_Widget SHALL render a single centred message "No live matches right now" using `text-slate-500` and `text-sm` typography, with no Match_Cards or skeleton cards visible.

16. WHEN a poll to `/api/matches/live` fails (network error or non-2xx response) after the initial load has succeeded, THE Scoreboard_Widget SHALL retain the previously displayed Match_Cards and SHALL render a small inline error indicator (e.g., a `WifiOff` icon with `text-red-400`) in the widget header without clearing the match list.

### Requirement 3: Upcoming Cricket Tournaments Block

**User Story:** As a cricket fan on the CricketVerse.AI Home page, I want to see a list of upcoming cricket tournaments and series, so that I can plan which events to follow and understand the cricket calendar at a glance.

#### Acceptance Criteria

1. THE System SHALL expose a `/api/tournaments/upcoming` REST endpoint that returns a JSON object with a `tournaments` array, where each element is a Tournament object.

2. WHEN the RapidApiCricketProvider is enabled, THE Tournament_Provider SHALL fetch data from the RapidAPI `/series/v1/upcoming` path and normalise each series entry into a Tournament object containing exactly these fields: `seriesId` (string), `name` (string), `startDate` (string, ISO 8601 YYYY-MM-DD), `endDate` (string, ISO 8601 YYYY-MM-DD), `format` (one of `"T20"`, `"ODI"`, `"Test"`, `"T10"`, or `"Other"`), `teams` (array of strings, up to four team/country names), and `status` (one of `"Upcoming"`, `"Ongoing"`, or `"Completed"`).

3. IF the RapidApiCricketProvider is not enabled (Simulator_Fallback mode), THEN THE `/api/tournaments/upcoming` endpoint SHALL return a static `tournaments` array containing at least four hardcoded Tournament objects that collectively cover at least three distinct formats (T20, ODI, and Test must each appear at least once).

4. IF the RapidApiCricketProvider is enabled AND the RapidAPI request to `/series/v1/upcoming` fails for any reason, THEN THE `/api/tournaments/upcoming` endpoint SHALL return a JSON response with HTTP status 502 containing an empty `tournaments` array and an `error` string field describing the failure.

5. THE Tournament_Provider SHALL convert raw timestamp or date values from the RapidAPI response into ISO 8601 date strings in `YYYY-MM-DD` format for both `startDate` and `endDate`. IF a date value cannot be parsed, THE Tournament_Provider SHALL set the corresponding field to `"unknown"`.

6. THE Tournament_Block SHALL be rendered on the Home page below the Scoreboard_Widget and above the existing PulsePlay Arena grid.

7. THE Tournament_Block SHALL display each Tournament object as a Tournament_Card. Each Tournament_Card SHALL show: the tournament `name`, the `startDate` and `endDate` in human-readable format (e.g., "15 Jan 2026"), a format badge, up to four team/country names from the `teams` array, and a status badge reflecting the `status` field.

8. WHEN the `tournaments` array contains more than three entries, THE Tournament_Block SHALL render all Tournament_Cards in a single horizontally scrollable row with `overflow-x: auto` and `flex-nowrap`, so that no card wraps to a second line.

9. THE Tournament_Block SHALL call `/api/tournaments/upcoming` exactly once on component mount. It SHALL NOT set up a polling interval. IF the fetch fails, THE Tournament_Block SHALL display an inline error message ("Could not load tournaments") using `text-red-400` and `text-sm` typography without retrying automatically.

10. WHEN the Tournament_Block is in a loading state (fetch has been initiated but not yet resolved), THE Tournament_Block SHALL render three skeleton placeholder cards using `animate-pulse` with `bg-slate-700/30`, each matching the fixed width and height of a real Tournament_Card.

11. THE Tournament_Card format badge SHALL use the following CSS classes: `badge-live-cyan` for T20, `badge-live-green` for ODI, a custom amber badge (`bg-amber-500/15 text-amber-300 border border-amber-500/25`) for Test, and a custom purple badge (`bg-purple-500/15 text-purple-300 border border-purple-500/25`) for T10. Formats classified as `"Other"` SHALL use the default `badge-live` class without a color modifier.

12. THE Tournament_Card SHALL derive the human-readable date string from the ISO 8601 `startDate` field using the format `"D MMM YYYY"` (e.g., "15 Jan 2026"). IF `startDate` is `"unknown"`, THE Tournament_Card SHALL display "TBD" in place of the date.

13. WHEN a Tournament object has `status` equal to `"Ongoing"`, THE Tournament_Card SHALL render a pulsing dot using the `animate-pulse-live` CSS class (a `span` with class `h-1.5 w-1.5 rounded-full bg-red-400 animate-pulse-live`) adjacent to the status badge, consistent with the live match indicators used elsewhere on the page.

14. WHEN the `tournaments` array is empty and the fetch has completed without error, THE Tournament_Block SHALL render a single centred message "No upcoming tournaments" using `text-slate-500` and `text-sm` typography, with no Tournament_Cards or skeleton cards visible.

15. THE Tournament_Provider SHALL deduplicate Tournament objects by `seriesId` before returning the list. IF a series entry has a null or missing `seriesId`, THE Tournament_Provider SHALL assign it a deterministic fallback ID derived from the series `name` and `startDate` fields (e.g., a hash or slug) to enable deduplication. The final `tournaments` array SHALL contain at most one entry per unique `seriesId`.

16. THE `/api/tournaments/upcoming` endpoint SHALL return the `tournaments` array sorted by `startDate` in ascending order (earliest date first). Entries with `startDate` equal to `"unknown"` SHALL be placed at the end of the sorted list.

17. THE `/api/tournaments/upcoming` endpoint SHALL return at most 20 Tournament objects in a single response. IF the source data contains more than 20 entries after deduplication and sorting, THE Tournament_Provider SHALL truncate the list to the first 20 entries (earliest by `startDate`).
